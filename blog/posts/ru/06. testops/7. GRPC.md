## 1. Что такое gRPC? (База для собеседования)
**gRPC** (Google Remote Procedure Call) — это высокопроизводительный фреймворк для вызова удаленных процедур. 
Если REST — это про «ресурсы и документы», то gRPC — про «вызов функций на удаленной машине».

**Три кита gRPC:**

1. **Protocol Buffers (Protobuf):** Язык описания контракта. Ты не пишешь JSON вручную, а описываешь структуру данных и методов в `.proto` файлах. Из этих файлов код (клиент и сервер) генерируется автоматически.
2. **Бинарная сериализация:** Данные передаются не в текстовом JSON, а в сжатом бинарном формате. Это делает передачу быстрее, а размер payload — меньше.
3. **HTTP/2:** В отличие от HTTP/1.1 (который использует REST), HTTP/2 поддерживает мультиплексирование (множество запросов в одном соединении), сжатие заголовков и **стриминг** (потоковую передачу данных).

## 2. REST vs gRPC: Шпаргалка для интервью
На собеседовании тебя почти наверняка попросят их сравнить. Держи эту структуру в голове:

| Характеристика | REST | gRPC |
| :--- | :--- | :--- |
| **Формат данных** | JSON / XML (текст) | Protobuf (бинарный) |
| **Протокол** | HTTP/1.1 (чаще) | HTTP/2 |
| **Контракт** | Swagger / OpenAPI (опционально) | `.proto` файлы (строго обязательно) |
| **Стиль** | Ресурсы (GET, POST, PUT, DELETE) | Методы / Функции (RPC) |
| **Стриминг** | Сложно (SSE, WebSockets) | Встроено (Client, Server, Bidirectional) |
| **Где используется** | Внешние API (для фронтенда, 3-х сторон) | Внутренние API (между микросервисами) |

## 3. Работа с gRPC в QA Automation (Практика)
Как автотестировщику, тебе не нужно писать сервер на gRPC. Твоя задача — **тестировать контракт, генерировать клиенты и проверять бизнес-логику**.

**Шаг 1. Работа с контрактом (.proto)**
Разработчики скидывают тебе `.proto` файл. Ты смотришь в него, чтобы понять, какие методы есть, какие поля обязательны, а какие нет.
*Лайфхак для QA:* Проверяй, что `.proto` файл версионируется и лежит в репозитории вместе с кодом.

**Шаг 2. Генерация клиента**
Тебе не нужно парсить бинарный Protobuf вручную! Ты берешь `.proto` файл и с помощью компилятора (`protoc`) генерируешь клиентский код на своем языке (Java, Python, C#). 
*В автотестах ты просто импортируешь сгенерированные классы и вызываешь методы как обычные функции.*

**Шаг 3. Написание автотестов**
Ты создаешь gRPC-клиент в коде, передаешь туда сгенерированные объекты сообщений (Messages) и проверяешь ответ.
```java
// Пример на Java (псевдокод)
UserServiceGrpc.UserServiceBlockingStub stub = UserServiceGrpc.newBlockingStub(channel);
GetUserRequest request = GetUserRequest.newBuilder().setUserId(123).build();
User response = stub.getUser(request);
assertEquals("Вика", response.getName());
```

**Шаг 4. Тестирование стриминга (Advanced)**
Если сервис отдает данные потоком (например, видео или логи), ты пишешь тест, который подписывается на стрим, читает данные по частям (chunks) и проверяет, что они приходят в правильном порядке и без обрывов.

## 4. Инструменты QA для gRPC
Что добавить в резюме или использовать в работе:

1. **Postman** — Да, он уже давно поддерживает gRPC! Можно импортировать `.proto` файл и отправлять запросы через UI.
2. **grpcurl** — Консольная утилита. Аналог `curl`, но для gRPC. Незаменима для быстрого ручного тестирования и написания bash-скриптов.
3. **BloomRPC / Crestdelva** — Специализированные GUI-клиенты для gRPC (удобно для ручного исследования API).
4. **ghz** — Отличный инструмент для **нагрузочного тестирования** gRPC (аналог JMeter, но заточен под gRPC и стриминг).
5. **Mock-серверы** (например, на базе WireMock или специализированные gRPC-mock) — чтобы тестировать свой сервис, пока разработчики не подняли смежный микросервис.

## 6. Топ-3 вопроса на собеседовании (Проверь себя)
1. **Вопрос:** В чем главная разница между REST и gRPC с точки зрения производительности и почему?
   * *Ожидаемый ответ:* gRPC использует бинарную сериализацию (Protobuf) вместо текстового JSON и работает поверх HTTP/2, что дает мультиплексирование и меньший оверхед.
2. **Вопрос:** Как ты будешь тестировать gRPC API, если бэкенд, который должен его отдавать, еще не готов?
   * *Ожидаемый ответ:* Я возьму `.proto` контракт, подниму mock-сервер (или использую инструменты вроде WireMock/gRPC mock), настрою его на отдачу захардкоженных ответов и напишу автотесты на своем сервисе-клиенте.
3. **Вопрос:** Что такое Protocol Buffers и зачем они нужны в тестировании?
   * *Ожидаемый ответ:* Это язык описания контракта. Для QA это источник истины (Single Source of Truth). По нему мы генерируем клиенты для тестов, проверяем валидность полей и понимаем, какие методы доступны.
